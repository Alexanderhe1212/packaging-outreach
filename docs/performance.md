# 五分钟目标与双账号运行

目标是**从一轮 AI 获客开始，到该客户的 SMTP final acceptance 约 300 秒**，包含官网来源、邮箱、产品方案、单张 A/B 图、正文、排队与发送。它是观测目标，不是杀进程的超时。超时仍继续处理，不能为了计时达标取消图片任务或重复投递。

规划预算（不是实测承诺）：研究与官网 90 秒，方案与参考下载 20 秒，图片 150 秒，正文及一次事实检查 25 秒，发送 15 秒。模型拥堵、官网访问、限流或 SMTP 都可能超预算。**全流程耗时与相邻两封发送的间隔分别统计**：流水线可以提高产出频率，但不会把单客户实际耗时变短到虚构的数值。

## 已实现的优化

- 同一工作目录的账号共用发现队列，轮流分配新研究；候选域名在官网抓取和生图前排除重复。分开的工作目录不共享防重记录。
- 每账号两条概念处理通道、独立正文/发送通道；已就绪邮件优先。未完成客户的队列上限包含运行中任务，避免无边界堆积。
- 共享 API 并发控制默认研究 1、文字 2、图片 2，避免两个账号同时把同一 Key 打满。提高并发须匹配服务实际额度；盲目增加会引起排队和 429。
- 官网结果缓存 15 分钟（最多 1 小时），保留原验证时间；产品图片持久缓存。规划和参考图下载并行。
- 每客户一轮研究、一次方案、一次生图、一次正文加事实核对；不做反复美观评分或自动重绘。
- 方案、图片、正文 API 可以分别选择模型。参数只在显式配置时传递，不擅自切换付费服务。

使用 [双账号示例](../examples/two-accounts.json)，填写各自 sender、WhatsApp、签名及邮箱配置。保留同一个 workspace；每个账号的邮箱验证记录独立。示例图片参数 `quality: medium`、`size: 1536x1024` 需服务支持；它们不是速度保证。`input_fidelity` 只用于支持该参数的模型，不要盲目添加。

[OpenAI 延迟指南](https://developers.openai.com/api/docs/guides/latency-optimization)建议减少串行请求、并行独立步骤和减少不必要输出；[图片文档](https://developers.openai.com/api/docs/guides/image-generation)说明尺寸和质量可调，复杂图片请求可能较慢。第三方接口的行为以其文档及实际响应为准。

## 看实测结果

```bash
python3 -m packaging_outreach --config ../my-outreach/outreach.json metrics
```

网页与 `status` 也显示这些数据：

- `accepted_end_to_end`：从研究任务建立到 SMTP 接受，含排队；p50、p95、样本数。
- `prepared_end_to_end`：仅生成 `.eml` 的耗时，绝不算作真实发送。
- `accepted_interval`：同一账号相邻 SMTP 接受的时间间隔。
- `stages`、`completed_api_calls`：阶段/调用耗时，用于定位瓶颈；API 并发等待包含在调用计时中。
- `over_target`、`blocked`、`unknown`：超目标或尚未完成的客户，避免只展示成功样本。

旧任务没有完整起点的不倒推成精确速度。报告窗口是最近 500 个客户任务和 2000 条阶段记录。要证明“五分钟一封”，需配置真实 API 与邮箱并观察连续真实样本；离线测试只证明调度、计时和恢复逻辑。

## 后续优化顺序

先根据 p95 找到最慢阶段，再对同一组产品比较模型、图像大小和质量，记录可用图比例及调用成本。其次优化来源适配与失败类别。批量检索、多租户、计费等应建立在真实速度与效果数据上，不宜先用更多并发掩盖错误产品图或无效邮箱。
